# Foodies API

Базовий шлях: `/api`. Тіла запитів і відповіді мають формат JSON, крім завантаження фотографій через `multipart/form-data`. Усі ID передаються рядками з 24 шістнадцяткових символів. Дати мають формат ISO 8601 у UTC.

Опис API за [ТЗ проєкту](https://docs.google.com/spreadsheets/d/1RQo9l60o5jiArDLVl9Gl7Gjq2kNolByJQ6-ERVR0Q8w/edit). Для ще не реалізованих маршрутів нижче наведено запропонований контракт.

## Стан реалізації

| Частина | Стан |
| --- | --- |
| `GET /api/health` | Реалізовано |
| `GET /api/recipes`: фільтри, пагінація, дані автора | Реалізовано |
| `GET /api/recipes/:id`: автор, інструкції та інгредієнти | Реалізовано |
| `GET /api/recipes/popular`: чотири популярні рецепти | Реалізовано |
| `GET /api/recipes/own`: свої рецепти з пагінацією | Реалізовано |
| `DELETE /api/recipes/:id`: видалення власного рецепта | Реалізовано |
| `POST /api/recipes`: створення з фото та інгредієнтами | Реалізовано |
| HTTP-маршрути обраного та `isFavorite` | Заплановано, BE-04 |
| Auth і users | Реалізовано; формати наведені нижче |
| Довідники, підписки та відгуки | Заплановано |
| Swagger UI на `/api-docs` | Реалізовано для маршрутів рецептів |

Публічні маршрути доступні без входу. Для приватних потрібен заголовок `Authorization: Bearer <accessToken>`.

## Відповіді та помилки

Для рецептів один об'єкт: `{ "data": { ... } }`. Список без пагінації: `{ "data": [ ... ] }`. Auth і users повертають власні формати, описані у відповідних розділах.

Список із пагінацією:

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "limit": 9,
    "total": 0,
    "totalPages": 0
  }
}
```

`total` рахується після застосування всіх фільтрів. Початково `page=1`, `limit=9`; `limit` від 1 до 100. Обидва параметри мають бути цілими додатними числами. Для сторінки за межами результатів повертається `200` і порожній `data`; номер запитаної сторінки не змінюється. Коли результатів немає, `totalPages=0`.

Помилка:

```json
{
  "success": false,
  "message": "Invalid query parameters",
  "errors": [
    { "field": "limit", "message": "Must be an integer from 1 to 100" }
  ]
}
```

`errors` є лише для помилок окремих полів. Успішний `204` не містить тіла.

| Статус | Значення |
| --- | --- |
| 200 | Читання, оновлення або повторне додавання вже наявного зв'язку |
| 201 | Створено користувача, рецепт або новий зв'язок |
| 204 | Вихід, видалення рецепта або зв'язку |
| 400 | Невалідні параметри, JSON або поля форми |
| 401 | Відсутній, прострочений чи недійсний токен |
| 403 | Немає прав на дію |
| 404 | Об'єкт або маршрут не існує |
| 409 | Конфлікт, наприклад уже зайнятий email |
| 413 | Завеликий файл |
| 415 | Створення рецепта без multipart/form-data |
| 500 | Внутрішня помилка без технічних подробиць у відповіді |
| 502 | Не вдалося завантажити фото в Cloudinary |

## Рецепти

### GET /api/recipes

Публічний список. Параметри передаються в query:

| Параметр | Значення |
| --- | --- |
| category | Назва категорії з `/api/categories`, до 100 символів |
| area | Назва регіону з `/api/areas`, до 100 символів |
| ingredientId | ID інгредієнта з `/api/ingredients` |
| ownerId | ID автора, якщо потрібні рецепти для його профілю |
| page | Номер сторінки, початково 1 |
| limit | Кількість рецептів, початково 9, максимум 100 |

Фільтри застосовуються разом. Назви category та area мають точно збігатися зі значеннями довідників. Пробіли на початку й у кінці прибираються; порожні фільтри ігноруються. Без category повертаються всі категорії. Невідомі та повторні параметри повертають `400`.

Сортування: `createdAt DESC`, потім `id DESC`. Це зберігає порядок між сторінками, коли дати рецептів збігаються. Зсув `(page - 1) * limit` не може перевищувати 2147483647.

Приклад запиту:

```http
GET /api/recipes?category=Seafood&area=Japanese&ingredientId=640c2dd963a319ea671e372c&page=1&limit=9
```

Відповідь `200`:

```json
{
  "data": [
    {
      "id": "640cd5ac2d9fecf12e8897f9",
      "title": "Salmon salad",
      "description": "Salmon with vegetables",
      "thumb": "https://example.com/recipes/salmon.jpg",
      "category": "Seafood",
      "area": "Japanese",
      "time": 30,
      "createdAt": "2026-11-11T10:00:00.000Z",
      "owner": {
        "id": "64c8d958249fae54bae90bb9",
        "name": "Olena",
        "avatar": null
      }
    }
  ],
  "pagination": { "page": 1, "limit": 9, "total": 1, "totalPages": 1 }
}
```

`owner` містить `id`, `name`, `avatar`, без email, пароля й даних сесії. `thumb` містить URL фотографії, `avatar` може бути null.

Поле `isFavorite` буде додано в BE-04: false для гостя, для користувача залежить від його обраного. Поки поле відсутнє. Каталог залишиться публічним. Відповіді з особистим обраним не можна кешувати спільно для всіх користувачів.

### GET /api/recipes/:id

Публічний. Повертає `{ "data": recipe }`. До полів картки додаються `instructions` та `ingredients`:

```json
{
  "instructions": "Cook the salmon and mix with vegetables.",
  "ingredients": [
    {
      "id": "640c2dd963a319ea671e372c",
      "name": "Salmon",
      "img": "https://example.com/ingredients/salmon.png",
      "measure": "400 g"
    }
  ]
}
```

Інгредієнти повертаються за `id ASC`; якщо їх немає, `ingredients` містить порожній масив. `ingredients[].name` та `img` можуть бути null у початкових даних; frontend показує placeholder для відсутнього зображення. Довгі описи та інструкції початкових рецептів не обрізаються.

ID має містити рівно 24 шістнадцяткові символи. Великі літери приймаються та переводяться в малі; пробіли в ID не допускаються. Неправильний формат повертає `400`, `{ "success": false, "message": "Invalid recipe ID" }`. Відсутній рецепт повертає `404`, `{ "success": false, "message": "Recipe not found" }`.

### GET /api/recipes/popular

Публічний. Відповідь `{ "data": [recipeCard] }`, максимум чотири рецепти. Популярність дорівнює кількості різних користувачів, які додали рецепт в обране. При однаковому значенні порядок визначають `createdAt DESC`, потім `id DESC`. Рецепти без збережень можуть заповнити решту місць. Параметрів пагінації немає.

Популярність рахується за таблицею `Favorite`, де пара користувач/рецепт унікальна. Якщо рецептів менше чотирьох, повертаються всі наявні; для порожнього каталогу відповідь `{ "data": [] }`.

Маршрут не приймає query-параметрів. Зокрема `page`, `limit` і фільтри повертають `400` з повідомленням `Invalid query parameters` та масивом `errors` для переданих полів. `/popular` оголошений перед `/:id`.

### POST /api/recipes

Приватний. Формат `multipart/form-data`; браузер сам задає Content-Type з boundary. Не встановлювати його вручну при надсиланні FormData.

| Поле | Формат |
| --- | --- |
| photo | Один JPEG, PNG або WebP, до 5 МіБ |
| title | Непорожній текст, максимум 255 символів |
| description | Непорожній текст, максимум 200 символів |
| category | Назва наявної категорії |
| area | Назва наявного регіону |
| time | Ціле число хвилин від 1 до 2147483647, передане як текст |
| instructions | Непорожній текст, максимум 1000 символів |
| ingredients | JSON-рядок масиву `{ ingredientId, measure }` |

Усі поля обов'язкові. Потрібен хоча б один інгредієнт. `ingredientId` має існувати та не повторюватись у рецепті, зокрема з іншим регістром літер; `measure` є непорожнім текстом до 100 символів. Зайві поля, включно з `ownerId`, відхиляються. Текстові поля обрізаються лише по краях. Для фото перевіряються MIME, сигнатура та ліміт 5 МіБ; порожній файл не приймається.

```javascript
const form = new FormData();
form.append("photo", file);
form.append("title", "Salmon salad");
form.append("description", "Salmon with vegetables");
form.append("category", "Seafood");
form.append("area", "Japanese");
form.append("time", "30");
form.append("instructions", "Cook the salmon and mix with vegetables.");
form.append("ingredients", JSON.stringify([
  { ingredientId: "640c2dd963a319ea671e372c", measure: "400 g" }
]));
```

Власник визначається за авторизацією, а не за тілом запиту. Рецепт одразу стає публічним. Відповідь `201`, `{ "data": recipe }` з ID, за яким frontend відкриває `/recipe/:id`.

Рецепт і його інгредієнти зберігаються в одній транзакції. Відповідь містить ті самі поля, що й `GET /api/recipes/:id`. Фото завантажується тільки після перевірки полів і довідників. Якщо запис у БД не вдався, сервер намагається видалити завантажене фото з Cloudinary. Якщо очищення також не вдалося, public ID записується в журнал для повторного видалення вручну.

Невалідні поля, відсутнє фото, неправильний формат фото або пошкоджена multipart-форма повертають `400`. Помилки вказують поле: `photo`, `time`, `ingredients` або, наприклад, `ingredients.0.measure`. Завелике фото повертає `413`, інший Content-Type запиту `415`. Збій Cloudinary повертає `502`; як і для `500`, тіло відповіді `{ "success": false, "message": "Internal Server Error" }`.

Обмеження 200/1000 стосуються створення нового рецепта. Початкові рецепти з довшими текстами читаються без обрізання.

### DELETE /api/recipes/:id

Приватний, тільки для власника. Успіх `204`; немає рецепта `404`; чужий рецепт `403`. Разом із рецептом видаляються його зв'язки з інгредієнтами та обраним. Лічильники й список популярних враховують видалення; frontend оновлює список і лічильники після успішного запиту. Читання видаленого рецепта повертає `404`.

Власник береться з перевіреного access-токена (`req.user.sub`). Поля `ownerId` у query або тілі не змінюють власника запиту. ID перевіряється так само, як у деталях рецепта: неправильний формат повертає `400`, великі літери переводяться в малі. Повторне видалення повертає `404`. Довідник інгредієнтів та облікові записи користувачів залишаються.

Фото, завантажене через цей API, видаляється з Cloudinary після видалення рецепта. Якщо Cloudinary недоступний, відповідь залишається `204`, а public ID фото записується в журнал для повторного очищення. Зовнішні фото початкових рецептів не видаляються.

### GET /api/recipes/own

Приватний. Приймає лише `page` та `limit`, початково 1 і 9, максимум 100 рецептів на сторінку. Формат `{ data, pagination }`, як у каталозі; `pagination` містить `page`, `limit`, `total`, `totalPages`. `total` враховує тільки рецепти поточного користувача. Порядок: `createdAt DESC`, потім `id DESC`. Порожній список і сторінка за межами результатів повертають `200`.

Власник береться з `req.user.sub`; `ownerId`, фільтри каталогу, невідомі та повторні параметри повертають `400`. Маршрут оголошений перед `/:id`. Відповідь містить `Cache-Control: private, no-store`.

### PUT /api/recipes/:id/favorite

Заплановано в BE-04 разом із DELETE favorite, GET favorites та полем `isFavorite`.

Приватний, без тіла. Додає наявний рецепт до обраного поточного користувача. Перший запит повертає `201`, повторний `200`; дубль не створюється, популярність не збільшується вдруге.

```json
{
  "data": {
    "recipeId": "640cd5ac2d9fecf12e8897f9",
    "isFavorite": true
  }
}
```

Відсутній рецепт повертає `404`.

### DELETE /api/recipes/:id/favorite

Приватний, без тіла. Видаляє тільки зв'язок поточного користувача, не сам рецепт. Відповідь `204`, також якщо зв'язку вже немає. Після дії frontend оновлює картку, список обраного та лічильник.

### GET /api/recipes/favorites

Приватний. `page` та `limit`, відповідь зі списком карток і pagination. Порядок за датою рецепта та ID, як у каталозі. Усі картки мають `isFavorite=true`. Видалені рецепти не потрапляють ані в список, ані в total.

## Авторизація

Приватні маршрути рецептів використовують middleware `authenticate`. Він перевіряє JWT із заголовка `Authorization: Bearer <accessToken>` за `JWT_SECRET`, строк дії токена, рядковий `sub` і `type: "access"`. ID користувача доступний у `req.user.sub`. Без токена або з неправильним чи простроченим токеном відповідь `401`. Refresh-токен для цих маршрутів не підходить. Помилки middleware мають формат `{ "success": false, "message": "..." }`.

Access token повертається у JSON і діє 15 хвилин. Refresh token діє 7 днів та зберігається у HttpOnly cookie `refreshToken` зі шляхом `/api/auth`. У production cookie має `Secure` та `SameSite=None`, локально `SameSite=Lax`. Для запитів із cookie frontend використовує `withCredentials: true`, backend дозволяє credentials для origins з `ALLOWED_ORIGINS`.

| Маршрут | Доступ | Тіло | Результат |
| --- | --- | --- | --- |
| POST /api/auth/register | Публічний | `{ name, email, password }` | 201, `{ success: true, user, accessToken }` і refresh cookie |
| POST /api/auth/login | Публічний | `{ email, password }` | 200, такий самий формат |
| POST /api/auth/refresh | За refresh cookie | Без тіла | 200, `{ success: true, accessToken }`, оновлена cookie |
| POST /api/auth/logout | Приватний | Без тіла | 204, сесію та cookie анульовано |

Після реєстрації користувач автоматично авторизований. Неправильний email або пароль повертає `401`, зайнятий email при реєстрації `409`. Об'єкт user містить `id`, `name`, `email`, `avatar`, `createdAt`, без пароля й refresh token. Logout відкликає refresh-сесію; вже виданий access token діє до завершення своїх 15 хвилин.

Валідація реєстрації: name після trim від 2 до 255 символів, валідний email до 255 символів, пароль від 8 до 72 символів. Email переводиться в нижній регістр. Пароль не обрізається.

## Користувачі

### GET /api/users/current

Приватний. Поточний користувач:

```json
{
  "id": "64c8d958249fae54bae90bb9",
  "name": "Olena",
  "email": "olena@example.com",
  "avatar": null,
  "recipesCount": 1,
  "favoritesCount": 5,
  "followersCount": 2,
  "followingCount": 4,
  "recipes": [
    {
      "id": "640cd5ac2d9fecf12e8897f9",
      "title": "Salmon salad",
      "description": "Salmon with vegetables",
      "thumb": "https://example.com/recipes/salmon.jpg"
    }
  ]
}
```

### GET /api/users/:id

Приватний. Повертає `id`, `name`, `email`, `avatar`, `recipesCount`, `followersCount` та `recipes` без обгортки `data`. Поля `isFollowing` поки немає. Елементи recipes містять `id`, `title`, `description`, `thumb`, як у поточному профілі.

Рецепти автора отримуються окремо через `GET /api/recipes?ownerId=:id&page=1&limit=9`.

### PATCH /api/users/current/avatar

Приватний. FormData з одним полем `avatar`, JPEG, PNG або WebP до 5 МіБ. Відповідь `200`, `{ "message": "Avatar updated successfully", "user": { "id": "...", "name": "Olena", "email": "olena@example.com", "avatar": "https://example.com/avatar.jpg" } }`. Міняється лише аватар поточного користувача. Відсутній файл повертає `400`, `{ "error": "Avatar file is required" }`. Валідація фото рецептів окрема; її формати помилок не поширюються на аватар.

## Підписки

Запропонований контракт, маршрути ще не реалізовані.

| Маршрут | Параметри | Результат |
| --- | --- | --- |
| GET /api/users/:id/followers | page, limit | Підписники вказаного користувача |
| GET /api/users/following | page, limit | Підписки поточного користувача |
| PUT /api/users/:id/follow | Без тіла | 201 для нового зв'язку, 200 для наявного |
| DELETE /api/users/:id/follow | Без тіла | 204, також при повторному запиті |

Усі маршрути приватні. Списки повертають pagination. Пропонований початковий limit для цих списків 5, максимум 100; порядок за `id ASC`. Підписка на себе повертає `400`, неіснуючий користувач `404`. Після PUT відповідь `{ "data": { "userId": "...", "isFollowing": true } }`. Зв'язки і лічильники обох користувачів змінюються разом.

Картка користувача в списку:

```json
{
  "id": "64c8d958249fae54bae90bb9",
  "name": "Olena",
  "avatar": null,
  "recipesCount": 3,
  "isFollowing": false,
  "recipes": [
    { "id": "640cd5ac2d9fecf12e8897f9", "thumb": "https://example.com/recipes/salmon.jpg" }
  ]
}
```

`recipes` містить до чотирьох останніх рецептів за createdAt та ID. Email і дані сесії в картки списку не включаються.

## Довідники та відгуки

Запропонований контракт, маршрути ще не реалізовані.

Публічні маршрути без пагінації, відповідь `{ "data": [...] }`:

| Маршрут | Поля елемента |
| --- | --- |
| GET /api/categories | id, name |
| GET /api/areas | id, name |
| GET /api/ingredients | id, name, img |
| GET /api/testimonials | id, testimonial, owner: { id, name } |

Категорії та регіони відсортовані за name, потім id. Інгредієнти так само; відсутня назва або img повертається як null. Для відгуків пропонується порядок за id. Фотографії категорій беруться з assets frontend; API їх не завантажує.

## Завантаження файлів і обране

Фото рецепта зберігає URL у `thumb` і public ID Cloudinary у внутрішньому полі `photoPublicId`. Міграція `20261112121718_add_recipe_photo_public_id` додає nullable стовпець `photo_public_id`. Його немає в HTTP-відповідях. Зовнішні URL початкових рецептів не видаляються з Cloudinary. Допоміжна функція для аватарів, як і раніше, повертає лише URL.

Обране зберігається в таблиці `Favorite` (`favorites`) з полями `userId` та `recipeId`. Пара цих полів є первинним ключем, тому дублікати неможливі. При видаленні користувача або рецепта відповідні зв'язки видаляються каскадно.

Міграція `20261111214554_add_favorites` переносить наявне обране з масиву `User.favoriteRecipeIds`, прибирає повтори та пропускає посилання на відсутні рецепти. Після перенесення старий стовпець видаляється. Початкова міграція не змінюється. Код, що працює з обраним, має використовувати `prisma.favorite`; формат HTTP API від цього не змінюється. Після оновлення виконайте `npx prisma migrate deploy` і `npx prisma generate`.

## Документація Swagger

Swagger UI доступний на `/api-docs/`, JSON-схема на `/api-docs/openapi.json`. Описані шість операцій рецептів: каталог, деталі, популярні, власні, створення й видалення. Для приватних маршрутів використовується bearerAuth, для файлів multipart/form-data з binary-полем. Є параметри, тіла запитів, відповіді та приклади помилок. Auth, users і майбутні маршрути BE-04 поки не включені до Swagger.

## Health

`GET /api/health` повертає `200`:

```json
{ "success": true, "message": "Foodies API is running!" }
```

Перевіряє HTTP-сервер. Підключення до БД не перевіряє.
